# agent16/badapple：UEFI 下播放 Bad Apple!!

新增目录，不改动仓库内已有文件，也不改 `G:\New_Desktop\project\git\badapple-efi`（只读参考）。时间为 Asia/Shanghai，2026-11-22。由 `../anim/build-anim.py` 调用，产物进入动画候选的 payload。**尚未构建，也未上机。**

## 参考项目 rinsuki/badapple-efi（MIT，`db7c806`）

- Rust nightly + uefi-rs 0.8（2021 年的 git 版本），只支持 `x86_64-unknown-uefi`，跑在 QEMU/OVMF 上。
- 512×384 灰度，30 fps，自定义 RLE；运行时从卷根目录读取 `seek.bin` / `data.bin`（仓库里没有，要用 ffmpeg 生成）。
- **没有声音**：编码器虽然把音轨拷成 `music.mp4`，但播放器从来不读。rothko 固件也没有任何音频驱动，所以这里同样无声，不存在音量设置。
- 无限循环、不喂狗、出错就 panic，数据量也远超 payload 卷的剩余空间。

因此只借用思路，播放器和编码器都用 C 重写，工具链和 ImageView / RothkoAnim 相同。

## 组成

| 文件 | 作用 |
| --- | --- |
| `BaCodec.h` | "RBA1" 格式：32 字节头（带头部 CRC 与码流 CRC）+ 一条 LZMA 式自适应二进制区间编码码流。每帧先编码"与上一帧相同"位，再逐行编码"与上一帧同行相同"位，其余逐像素编码，概率由 12 位上下文决定（本帧已解码的 6 个邻居 + 上一帧同位置的十字 5 点 + 右上第二点）。播放器和编码器共用这一份解码代码 |
| `ba-encode.c` | 宿主机编码器。从 stdin 读 ffmpeg 输出的 8 位灰度帧，阈值 128 二值化，编码；超出预算时提前以退出码 3 结束。编码完成后把文件读回，用 `BaCodec.h` 逐帧解码并与输入逐像素比较，有任何不同则退出码 4。另外输出 1/4、1/2、3/4 处解码帧的 PGM 预览 |
| `BadApple.c` | 独立 AArch64 UEFI 应用，不依赖 EDK II 库，只用 GOP。启动时检查头部和码流 CRC，然后按屏宽等比放大（最近邻），居中显示，上方标题，下方时间、进度条和按键提示。按通用定时器计时，落后时只解码不绘制，保持实时。音量键暂停/继续，电源键或其它键回菜单，前 1.5 s 的按键丢弃。播完显示 THE END 2 s 后返回；`loop=1` 循环播放。每 500 ms 喂一次 MTK RGU 看门狗，并关闭 UEFI 看门狗 |
| `BaBlob.S` | `.incbin` 码流，符号 `gBaData` / `gBaDataEnd`，与 ImageView 的 `ImageBlob.S` 相同做法 |
| `build-badapple-efi.sh` | WSL：编译 ba-encode → 按画质阶梯逐级尝试（480×360@30、480×360@15、400×300@15、320×240@15、320×240@10、256×192@10、192×144@10、160×120@10），取第一个放得下的 → clang/lld/GenFw 链接 BadApple.efi |

文字字形取自 `../anim/AnimTables.h`（UniXNU Font.c / LaffStd，BSD）。

## 第三版（17:12，用户反馈"帧率从没有高于 10"）

分析（只读固件源码，未改固件）：

- UEFI 只在启动核上运行：固件里没有 MpServices，`PcdCoreCount=8` 只是描述信息。但解码按帧顺序依赖，多核对它帮助不大，瓶颈也不在解码。
- `RothkoDisplayDxe` 找到了 **2 个**扫描输出层（2026-11-15 的 pstore 日志："2 validated scanout layer(s)"）。它的 `Refresh()` 每 20 ms（TPL_CALLBACK 定时器）把整个帧缓冲（1248×4×2712 ≈ 13.5 MB）`CopyMem` 到第二层，再对 13.5 MB 做缓存清理。
- 帧缓冲 "Display Reserved" 在 MemoryMapLib 里映射为 **WRITE_THROUGH**。对 Cortex-A7xx 这类核心，写通内存通常按不可缓存处理，所以上面那次复制的每一次读取都直接访问 DRAM。另外 GOP `Blt()` 写完以后，还会再对每个像素做一次 `|= 0xFF000000`（读改写）。
- 结论：每秒 50 次整帧镜像复制抢占了启动核的大部分时间，播放器只能用剩下的时间。具体比例要靠第三版上机测出来。

改动（仍只改播放器）：

- 三种输出模式，音量下键循环切换，也可以用加载选项 `mode=0/1/2` 指定：
  - `GOP`：和第二版一样。
  - `GOP+SYNC`：解码、绘制、输出和等待期间都把 TPL 提到 TPL_CALLBACK，每帧只在循环开头降回 TPL_APPLICATION 一次。被挡住的刷新回调会合并成一次执行，所以镜像复制最多每帧一次，不再固定每秒 50 次。
  - `DIRECT+SYNC`（默认）：在 SYNC 的基础上，变化的行带直接写进 GOP 帧缓冲（只写不读，alpha 设为 0xFF），然后按 CTR_EL0 的行宽做 `dc cvac`，最后 `dsb sy`，跳过 Blt 的读回那一遍。像素格式不是 BGRX，或者帧缓冲信息不合理时，自动退回 GOP+SYNC。
- 信息栏多了一行：`模式 DEC a DRAW b OUT c FW d`，单位都是"毫秒/每呈现一帧"。FW = 墙钟时间减去播放器自己的工作和睡眠时间，也就是被固件回调（主要是显示刷新）占走的时间。

## 第四版（17:45，第三版实测 4–5 fps，最高不到 10）

为什么"视频去重、只传差异"在码流这一侧收益不大：码流已经是差分的（整帧相同 1 位、整行相同 1 位、其余按上下文做算术编码，平均每帧 385 B）。播放器第二版起就只重绘变化的行。瓶颈在显示这一侧：

- `RothkoDisplayDxe` 的 `Refresh()`（TPL_CALLBACK，20 ms 周期）每次都把整个帧缓冲（4992×2712 = 13.5 MB）`CopyMem` 到第二个扫描输出层，再清理缓存，然后才写 mutex 和 `DSI_START`。帧缓冲按 WRITE_THROUGH 映射，这次复制的读取基本都直接访问 DRAM。SYNC 模式只是把这次复制压到每帧一次，没有去掉它。
- 真正的"推帧"只有几次 MMIO 写：给 mutex 组的每个 bank 写 `MUTEX_EN(id)=1`，然后 `DSI_START` 先写 0 再写 1。

所以"上传差异"应该做在显示输出这一侧：

1. **OWN 模式（新默认）**：整个播放期间一直保持 TPL_CALLBACK，固件的 Refresh 不会执行。播放器按驱动 `ProbeScanouts()` / `ProbeMutex()` 的同一套规则，自己找到所有扫描输出层和 DSI0 mutex 组；只把**脏矩形**写进每一层，然后自己执行 mutex 和 DSI_START。推帧最短间隔 20 ms，和驱动一致。13.5 MB 的整帧复制不再发生。
   - 键盘扫描定时器同样会被挡住，所以按键改为直接读取：音量上读 GPIO196（pinctrl+0x260 的 bit4，低电平为按下）；电源键和音量下读 PMIC 0x91B 的锁存位（经 PMIF SID4，写 1 清除）。做法与 KeypadDeviceLib 完全相同，退出前会清掉锁存，避免菜单再收到一次回车。
   - 可用条件：有直接帧缓冲；帧缓冲本身是扫描输出层之一；只有一个 mutex 组匹配；PMIC 键中断已使能（0x90F 中对应位已置 1）。任何一项不满足，提示栏都会显示 `NO-OWN n`：1 = 没有直接帧缓冲，2 = 帧缓冲不是扫描输出层，3 = 没找到 mutex 组，4 = PMIC 按键不可用，5 = 播放中 PMIC 连续读失败（自动退回 DIRECT 模式）。此时会退回 DIRECT 模式。
   - 保险：OWN 模式下按住音量上 3 秒一定退出。看门狗由播放器自己喂。
2. **瓦片级脏矩形**：源画面切成 16×8 的瓦片，逐块和上一次绘制的画面比较。每 8 行为一条带，带内连续的脏瓦片合并成一个矩形（中间夹着的单个干净瓦片也并进去）；上下相邻、只有一段且列范围相同的带纵向合并。只对这些矩形做放大绘制和输出。
3. 模式：GOP → SYNC → DIRECT → OWN（音量下循环切换，也可以用 `mode=0..3` 指定），默认 OWN。
4. 统计行：`模式 DEC a DRW b OUT c FW d PX e%`，前四项单位是毫秒/每帧，PX = 每帧重绘的面积占视频区域的百分比。
